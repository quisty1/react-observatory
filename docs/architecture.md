# Архитектура React Observatory

## Разделение ответственности

```text
TSX редактора → Babel Worker → изолированный iframe
                                  ↓ SDK + Profiler
                             TraceEvent[]
                                  ↓
              IndexedDB ← ExperimentSession → JSON
                                  ↓
                             VideoBrief
                             ↙        ↘
                     Remotion Player  Node renderer → MP4
```

`domain/` не зависит от React-интерфейса. Здесь находятся Zod-контракты, сериализация, тайминги сцен и текстовые экспорты. `data/` определяет учебное содержание и проверку поведения. `runtime/` компилирует и запускает код. `components/` и `pages/` реализуют продукт. `video/` отвечает за воспроизводимые кадры. `server/` управляет локальной очередью.

## Контракты

- `LabDefinition` — учебный вопрос, два варианта кода, объяснение, схема, задания и предикат проверки.
- `TraceEvent` — монотонные `seq` и `time`, категория, область, подпись, данные и необязательная строка исходника.
- `ExperimentSession` — версия 1, исходник, параметры запуска и до 1000 событий. Ограничение компактного JSON — 8 МБ.
- `VideoBrief` — исходный и исправленный код, выбранные события, отдельно контрольные события, три подписи схемы, сценарий, темп и оформление.

Видеокомпозиция принимает сериализуемые данные. Доступ к iframe, IndexedDB, текущему времени и редактору из композиции не нужен.

## Исполнение и наблюдение

Babel удаляет TypeScript-аннотации и преобразует JSX в automatic runtime. Проверка импортов выполняется до преобразования модулей. Циклы и функции получают вызовы ограничения синхронного времени. Бюджет начинается заново в следующем обороте event loop, чтобы обычная анимация не исчерпывала его за несколько кадров.

Вызовы явных `trace.*` и `useSnapshot` получают номер исходной строки. SDK записывает действия, вызовы компонентов, снимки после layout effect и события жизненного цикла. Корневой `TraceBoundary` использует React Profiler: его `onRender` фиксирует коммиты. Это различные виды наблюдения, и интерфейс не приравнивает вызов компонента к коммиту.

Iframe имеет только `sandbox="allow-scripts"`, без same-origin. Runtime и библиотеки заранее собраны в локальный IIFE. CSP ограничивает подключения и загрузки; data/blob-медиа разрешены для служебного аудио Remotion Player. Межконтекстные сообщения проверяют `source`, `runId`, канал и структуру. Сообщения прежнего запуска не попадают в новую запись.

Development React используется внутри sandbox независимо от режима сборки основного интерфейса. Поэтому Strict Mode в опубликованном демо действительно демонстрирует development-проверки эффектов. Основной интерфейс собирается обычной production-сборкой React.

## Хранение и воспроизведение

IndexedDB содержит отдельные object stores: `sessions` и `settings`. У каждой лаборатории есть свой черновик и ответы. Сохранённая запись не заменяет новый черновик при просмотре; перенос в редактор выполняется отдельным действием «Продолжить эксперимент».

Текущее содержимое редактора и исходник выполняемой записи разделены. Незапущенные изменения отмечаются отдельно. JSON-экспорт сохраняет исходник именно записанного запуска. Выгрузка компактная: тот же лимит применяется при валидации, хранении и импорте.

Просмотр по шагам меняет выбранное событие и соответствующий фрагмент исходника. Он не пытается откатить состояние живого React-приложения. Для собственного кода без меток доступны результат, консоль и корневые коммиты.

## Учебная корректность

Автоматическая проверка использует наблюдаемое поведение. Например, batching требует перехода на +3 в пределах одного действия; три отдельных увеличения на 1 не подходят. Проверка ключей сравнивает финальный ввод перед перестановкой с состоянием задачи после неё.

Исходный и исправленный примеры записаны отдельно реальными действиями Playwright. Тесты подтверждают, что исходная запись не проходит целевую проверку, а исправленная проходит. Готовый ролик показывает исходную запись и отдельно обозначенный контрольный запуск исправления. Если пользователь создаёт видео из уже исправленного кода, текст объясняет решение. Произвольный код получает нейтральный отчёт.

## Видео и сервер

Время выражено в целых кадрах при 30 fps. Шесть глав по 240 или 300 кадров дают 48 или 60 секунд. Встроенный Player и `renderMedia` используют один `ExperimentExplainer`. Композиция `ProductTour` использует `Sequence` и шесть реальных экранов для минутного обзора продукта.

`POST /api/renders` принимает `{brief}`, проверяет Zod-контракт и возвращает 202 с идентификатором. `GET /api/renders/:id` сообщает статус и прогресс; `DELETE` отменяет ожидающую или активную задачу. Файл доступен через `/renders/:id.mp4` только для завершённого задания.

Состояния: `queued → bundling → rendering → done`, а также `error` и `cancelled`. Один рендер активен, до трёх ожидают. Параметры Remotion: H.264, CRF 20, три параллельных кадра. Сборка композиции кэшируется в процессе.

Последний job ID лаборатории хранится в sessionStorage. После возвращения в видеовкладку опрос восстанавливается, готовый файл снова доступен. Серверные статусы хранятся в памяти; после перезапуска сервер явно сообщает, что задание не найдено. Облачная очередь в эту версию не входит.

## Полная и статическая сборки

`npm run build` создаёт полную версию с BrowserRouter. Express раздаёт её после `npm start` и обрабатывает прямые переходы.

`npm run build:demo` создаёт статическую версию с HashRouter: прямые ссылки и обновление работают без правил перенаправления на хостинге. Этот режим явно отключает новый серверный MP4-экспорт. Все остальные возможности, включая готовые ролики, работают в браузере.
